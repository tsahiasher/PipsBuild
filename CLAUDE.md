# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Pips Build: a browser-only React + TypeScript + Vite app that reconstructs a Pips-style domino puzzle from a screenshot and lets the user play it. Hard constraints: no backend, no remote OCR/AI, no uploads, and no NYT branding or assets (styling is original). The `samples/gameN.jpg` screenshots are the vision regression fixtures: phone captures plus desktop captures (`game5` = `game4`'s puzzle, `game8` = `game7`'s) at different scales and aspect ratios. Each has a golden, `samples/goldens/gameN.json`: the recogniser's saved output in the app's puzzle-file format (it opens in the app via "Import puzzle file"). `icon.jpg` in the root is the README image, not a sample.

## Commands

- `npm run dev`: dev server. `npm run build`: typecheck (`tsc --noEmit`) plus static build to `dist/` (relative `base`, works from any static host).
- `npm test`: all Vitest suites. `npm run test:engine` / `npm run test:vision` run one side.
- Single test: `npx vitest run tests/engine/game.test.ts -t "repair mode"`.
- Tests and `npm run dev` can run at the same time (checked). Twice, in the same minute as starting a fresh dev server, a full `vitest run` reported every file as failed with "no tests" and passed when rerun; the cause was never found, so if that happens just run it again.
- `npm run count:solutions [-- game10] [--show]`: prints how many solutions each golden puzzle has (`--show` draws them: pips per square, and which squares share a domino). Use it to find out whether a puzzle with several solutions is a recognition mistake or genuine.
- `npm run save:goldens [-- game10 game3]`: runs the recogniser on every sample (or the named ones) and saves the result as `samples/goldens/gameN.json`. It prints `new` / `changed` / `unchanged` per sample, flags recogniser warnings and consistency errors, and leaves unchanged goldens untouched so `git diff samples/goldens` shows only real changes. A golden is only as right as the recogniser was when it was saved: review new or changed ones (git diff, or open the file with "Import puzzle file") before committing.
- `npm run check:chrome`: runs the real in-browser pipeline (Chrome JPEG decode → worker → recognizer) on every sample and diffs it against its golden, and checks the `?debug=1` panel, the editor's solvability strip and the animated turning of a domino, on a dev server and on a real production build. It starts its own dev server and uses the installed Chrome (`CHROME_PATH` overrides). Run it after any recognition change.
- `?debug=1` on the app's URL (dev server `http://localhost:5173/?debug=1`, or the deployed site) adds a "Debug: load a sample" card to the home screen with one button per `samples/gameN.jpg`; clicking one loads it exactly as if it had been uploaded. The `samples` plugin in `vite.config.ts` serves the images and a list (`/samples/index.json`) on the dev server and copies both into `dist/samples/` on build, so a deploy ships the screenshots too (about 1 MB; this is intended). `npm run check:chrome` tests the panel on a dev server and on a real production build.
- `npm run analyze [game1 game4 ...]`: prints each sample's reconstruction (default: all samples) as ASCII (grid, regions, badges, dominoes, confidence). Use it when touching `src/vision`. `BROWSER=1` analyses the Chrome-decoded pixels instead; `SKIP=1` skips glyph classification and shows glyph counts.
- `npm run train:glyphs`: regenerates `src/vision/glyphTemplates.ts` from the samples, labelled by their goldens (Node decode, Chrome decode, and ×0.6/×0.45 downscales). It prints badges whose glyph count is wrong and a leave-one-puzzle-out accuracy check. Rerun it after any change to glyph extraction or features, and before running the vision tests.

## Architecture

Three layers. Game rules never live in React components.

- `src/engine/` is pure game logic with no DOM.
  - `types.ts`: `Puzzle` (sparse `cells` keyed `"row,col"`, `regions`, `dominoes` with unique ids so duplicate values stay distinct pieces). A `Placement` is `{cellA, cellB}`, where value `a` sits on `cellA`. Placements are stored as cell ids, never pixels.
  - `placement.ts`: `canPlaceDomino` / `placeDomino` / `removeDomino` / `rotatePlacement` / `getBoardValues`. `rotatePlacement(p, pivot)` turns clockwise around a fixed pivot cell (default: the top/left cell); the UI keeps the pivot fixed for a whole selection, so four taps circle back to the start. `Rotation` 0–3 = A left / top / right / bottom.
  - `constraints.ts`: `evaluateRegion` → `{complete, valid, impossible}` for sum / lt / gt / eq / neq. All condition logic lives here.
  - `game.ts`: `gameReducer(puzzle, state, action)`. Owns the timer (`elapsedMs` + `startedAt`; actions carry `now`), `validationMode` (`normal` → `repair` the first time the board is full but wrong; repair survives removals and is cleared only by reset), solve detection (stops the timer, freezes the board), and `visibleErrors()`, which drives the red dots.
  - `solver.ts`: `countSolutions(puzzle, {maxSolutions, maxMs, collect})` counts distinct solutions with a depth-first search that always covers the first free square and checks each condition incrementally (sum/lt/gt with bounds from the pips on the dominoes, eq, neq), and returns `{count, complete, stoppedBy?, reason?}`. `complete` means the count is exact and 0 means provably unsolvable; otherwise it is "at least". Counting rule: arrangements are one solution when every condition holds the same pips and every square outside the conditions has the same pip, where a domino on two such squares counts either way round (`signature()` at each leaf; the search itself skips turning a domino whose squares share a condition, which cannot change the signature). Swapping identical dominoes, turning a double, 2|3 against 3|2 inside one condition, and re-pairing squares with the same pips are therefore one solution. `solveWorker.ts` runs it off the main thread.
  - `puzzleFile.ts`: the JSON save/import format (`pips-build-puzzle` v1; legacy `pip-studio-puzzle` still imports) with validation.
  - `puzzle.ts`: consistency checks (cells === 2 × dominoes, odd board pieces), `normalizePuzzle` (assigns a content-hash `id`; games are keyed by it), `badgeCell` (the region's lowest-then-rightmost cell. The badge sits on that cell's bottom-right corner, both in screenshots, where recognition relies on it, and in the app, which draws it above the translucent dominoes), `parseConstraint`.
- `src/vision/` is screenshot → `Puzzle`. It's pure TS over `{width, height, data}`, so the same code runs in a Web Worker (`worker.ts`, driven by `client.ts`) and in Node tests (`scripts/load.ts` decodes JPEGs with `jpeg-js`). It doesn't use OpenCV or Tesseract. Pipeline in `recognize.ts`:
  1. Dominoes: dark-outline rings of one common size; pips are counted as dark blobs per half.
  2. Board: mid-tone components containing the beige frame color.
  3. Pitch: tray domino width ÷ 1.45 as the prior; each board piece measures `n·pitch + 2·0.053·pitch`. Candidates are scored by board-dimension residuals and by whether the cell count equals 2 × dominoes.
  4. Cells: center-box coverage.
  5. Regions: adjacent cells are unioned when the seam between them matches both cells' colors (threshold 0.53; same-region seams score ≥ 0.7, boundaries ≤ 0.35). Unconstrained cells are detected by closeness to the neutral/frame color.
  6. Badges: strong-color mask → fill holes → morphological open (removes dashed borders) → components. Each badge maps to the region via `badgeCell`.
  7. Glyphs: the badge crop is resampled to a fixed scale (`GLYPH_REF_PITCH`) using bilinear interpolation of a whiteness score `L − 2·C`. It's then thresholded adaptively per badge (between the badge color and the brightest text), and restricted to the badge's own filled shape and its central zone (the badge notch holds pastel pockets). Pieces within a few pixels of each other are grouped (thin strokes of a small `>` break apart), then split into characters. Fragments are re-merged, and a blob too wide for its own height is split (touching digits). Three-character labels such as `>14` use a smaller font, so `normalizeLabelSize` rescales them to normal digit height before classification. Glyphs are classified against `glyphTemplates.ts` (vocabulary `0–9 < > = ≠`).

  Board connectivity counts badge and dash pixels as board. Otherwise a cell boxed in by borders and badges on every side can be cut off from its piece; this happened with Chrome's decode of `game6`.

  All thresholds are relative to the pitch. Never hard-code pixel coordinates.
- `src/ui/` is React. `Board.tsx` renders any puzzle as SVG (100 units per cell; region outlines via `boardGeometry.ts` loop tracing plus inset). `PlayScreen.tsx` handles interaction: Pointer Events with capture on the stable root element (not native DnD), snap preview via `computePreview`, tap-to-rotate in the tray, select-then-tap rotation on the board with a 2 s auto-deselect (an illegal tentative rotation reverts; legal rotations commit immediately), and keyboard control. The rotating domino is `SelectedDomino.tsx`: it is drawn in the pose it had when selected inside a group that CSS turns a quarter turn around the pivot square per tap (matching transform lists, so the browser animates it; an illegal turn that snaps back after 2 s animates back too, via `legalTurns`). Solving shows confetti and the best time (`bests` in storage). `EditorScreen.tsx` is both the verify screen and the manual builder; its sticky header holds the top bar and `SolveBanner` (the green/red solvability strip, fed by `useSolvability`, which counts in a worker 250 ms after the last edit, keeps showing the previous result dimmed meanwhile, and uses the limits in `solveMessage.ts`: 1,000 solutions or 2.5 s). The editor also has the screenshot overlay comparison, which uses `recognition.geometry` (`originX/originY/pitch` in image px).
- `src/App.tsx` + `src/state/storage.ts`: screen routing and localStorage persistence. `bests` (fastest time and solve count per puzzle id) is saved too; `loadState` fills it in for older saves. Games are kept per puzzle id. On load, running timers are frozen at `savedAt` (closed-browser time isn't counted), and a saved `play` screen reopens on Home with "Resume puzzle".

## Tests

- `tests/engine/*` cover the rules, the reducer and pip patterns.
- `tests/vision/recognize.test.ts` walks every `samples/gameN.jpg` (discovered from the folder) and asserts the reconstruction equals its golden: cells, regions with conditions, and domino order. Region ids, colours and the grid offset are not compared (`canonicalPuzzle` in `tests/vision/goldens.ts`). It also fails if a sample has no golden or a golden has no sample. Each sample is decoded by jpeg-js and, when `tests/vision/browser-decoded/gameN.png` exists, by Chrome's pixels too; the two decoders differ slightly, so both must pass. A sample without a PNG shows as skipped there; `npm run check:chrome` covers real Chrome regardless.
- `tests/vision/numbers.test.ts` repaints real badges with every value 0–24 and all operators, using real glyph pixels, and reads them at phone and desktop scale.
- `tests/engine/solver.test.ts` covers the counting rule (your examples: 3|3, 2|3 against 3|2 under "sum 5", turns across two conditions) and cross-checks 60 random puzzles, loose and tight, against an independent brute force that uses the engine's own `isSolved`. `tests/ui/solveMessage.test.ts` covers the strip's wording.
- `tests/ui/storage.test.ts` (a save from before best times still loads).
- `tests/vision/solvable.test.ts` counts the solutions of every golden puzzle and checks each against `isSolved`. Samples are expected to have exactly one solution; `MORE_THAN_ONE` in that file lists the ones that genuinely have several (game10: 3, verified by hand). A misread golden is usually unsolvable or ambiguous, so this also catches a bad golden being saved.

To add a sample screenshot:
1. Put `gameN.jpg` in `samples/` (the name must match `game<number>.jpg`).
2. `npm run save:goldens -- gameN`, then review the golden (and `npm run count:solutions -- gameN --show`: a puzzle should normally have exactly one solution, so several usually mean something was misread; if you have checked by hand that they are real, add it to `MORE_THAN_ONE` in `tests/vision/solvable.test.ts`): load the sample with the `?debug=1` button, or open `samples/goldens/gameN.json` with "Import puzzle file". If the recogniser got something wrong, fix the golden by hand (the editor's "Save puzzle to file" output works, or edit the JSON) and fix the recogniser until `save:goldens` agrees.
3. Optionally add `tests/vision/browser-decoded/gameN.png`: a lossless dump of `loadImageFile()`'s ImageData, taken in Chrome from the running dev server.
4. Run `npm run train:glyphs`, then `npm test` (dev server stopped) and `npm run check:chrome`.
